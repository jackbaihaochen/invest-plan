# 设计决策

倒序，新的在上。

## 2026-09-01 · 成長グラフは「元本の線」＋「実測の点」。過去の評価額は捏造しない

用户要资金成长曲线。**过去每一天的評価額在任何一份 CSV 里都不存在，也推不出来**
（要有逐日的基準価額和株価，两者都没有）。所以画三样东西，各自说清是什么：

1. **累计投入（元本）** —— 取引履歴の外部入出金を積み上げた線。完全准确。
2. **実測総資産** —— 保有商品 CSV を取り込むたびに1点だけ残す。今は1点、以後1回ごとに増える。
3. **これから** —— 今日の資産から複利で伸ばす2本（実績ペース / 計画）。

被否决的做法：把元本の線を「資産」と呼ぶ、あるいは今日の含み益率を過去に遡って掛ける。
どちらも 2025年1月の資産を断定することになる。`asOf` を今日に倒していたバグと同じ種類 ——
**持っていない情報を、持っているように見せる**。線の名前を間違えるだけで同じ嘘になる。

`valuePoints` は取り込み時にしか増えないので、始めるのが早いほど価値が出る。
第 3 阶段までは localStorage にしか無い（端末ローカル、サイトデータを消すと失われる）。

## 2026-09-01 · 年率は設定にして、実績年率（22.6%）は「期間つきの実績」として別に出す

金額加重の実績年率は 2024/03〜2026/08 で 22.6%。見通しの既定は 7% のまま。
**この差を黙って放置すると「なぜ実績を使わないのか」に答えられない**ので、
年率を選べる設定にした（0/3/5/7/10%）。ツール側が利回りを決めない形にする。

22.6% を見通しに使わないのは、2.4年の、しかも上げ相場を含む1本の実績だから。
表示は必ず期間を添える（「2024/03/25起」）—— 期間の無い「年率」は将来の約束に読める。

## 2026-09-01 · 手动记录与 CSV 不相加，用 coverageEnd 接缝

CSV 里已经包含每一笔入金，手动记录只是 CSV 追上来之前的临时占位。
以 adjusthistory 文件里最大的 `受渡日` 为界：之前用 CSV，之后用手动记录。
手动记录被 CSV 匹配上就退位（不再单独计数），匹配不上就标红要求处理。

替代方案「两边相加」会重复计算；「只用 CSV」会让当月进度停滞两周，
打卡机制就失去反馈。接缝法两个问题都没有，代价是要实现一个匹配规则
（金额相等 + 受渡日 ±5 天）。

`unmatched` 状态是有意保留的功能而不是错误处理：它把「你以为投了但券商没收到」
暴露出来。上一版垮在数字不可信，这里让不一致可见。

## 2026-09-01 · ~~評価額只在 CSV 导入时更新~~ → 用基準価額メール日次化

**已被同日的下一条推翻。** 原结论基于「投資信託 69% 没有任何行情源」，
该前提不成立：楽天証券每个工作日发一封投信基準価額メール。

## 2026-09-01 · 投信の評価額は基準価額メールで日次更新する（前条を差し替え）

邮件价 × CSV 数量 = *** 円，与 CSV 自己的前日値（*** − 前日比 ***）
**分文不差**。单位两边都是每 1 万口日元，基準価額有 1 个工作日滞后。

日次更新覆盖率因此从 18% 升到 84.6%，混用实时与快照的取舍随之反转：
18% 实时时，总额既非当日也非快照日、无法解释；84.6% 实时时，
总额实质上是当日值，把停住的 15.4%（金 13.0% + 日本株 2.4%）按分类标注时点即可。

**硬规则：Gmail 只提供价格，永不提供数量、持仓或交易。** 上一版从約定メール
反推口数、误差逐笔累积，这是数字不可信的根源。数量只来自 CSV，每次导入重新锚定。

Apps Script 侧：用 Gmail 高级服务配 `gmail.readonly`（`GmailApp` 强制要
`https://mail.google.com/` 全权限）；读邮件只放在时间触发器里，
绝不能出现在公开的 `doGet`/`doPost` 路径上，否则 exec URL 就成了邮箱代理。

## 2026-09-01 · Google Sheet 读写分离：读走公开 CSV 端点，写走 Apps Script

读用 `https://docs.google.com/spreadsheets/d/<ID>/gviz/tq?tqx=out:csv&sheet=<name>`。
实测该端点对「知道链接的人可查看」的表格返回 `access-control-allow-origin: <请求源>`，
静态页面可直接 `fetch`，不需要「发布到网页」、不需要 API key、不需要代理。

写用一个部署成「任何人可访问」的 Apps Script Web App。选它而不是浏览器直连
Sheets API，是因为后者要建 GCP 项目、配 OAuth client、过同意画面，且 token 会过期；
而「任何人可访问」的 Apps Script 部署**完全不经过 OAuth 同意画面**，一次 5 分钟，之后不再碰。

上一版曾把 Apps Script 排除掉，理由是「agent 没法替用户完成授权和部署」——
那是 agent 能力的限制，不是用户的意愿；而且当时因隐私必须选「仅自己可访问」，
现在用户明确不在乎数据被看到，这个约束消失了。

代价：写路径依赖一个用户部署的服务。缓解：读路径不依赖它，所以它挂了看板照常显示。

## 2026-09-01 · 激励机制围绕「手动买入」，不围绕「每日打卡」

積立自动执行且每月封顶 15 万，要达到 40 万/月的目标必须主动补足差额。
这个补足动作是唯一可控、会重复、直接决定成败的行为，所以进度环和 streak 都挂在它上面。

否决了「今天没乱花钱」式的每日打卡：它和 1 亿目标之间只有间接因果，容易变成
贴在净值旁边的空计数器。每记一笔必须立刻换算成「到 1 亿提前了 N 天」，
因果可见是这个机制成立的前提。

## 2026-09-01 · 「投入」的口径是净入金，不是買付金額

用账户里已有的預り金买东西不增加总资产。把買付当投入会虚高进度。
口径必须在界面上写出来，并且用户自己记的数要和 CSV 里的入出金明细对账并排显示 ——
上一版垮在「数字用户不信任」，可追溯性从第一天就要有。
