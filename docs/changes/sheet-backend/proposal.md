# 第 3 阶段：数据搬到 Google Sheet，读写都走 Apps Script 令牌

**类别：A（推翻已记决策 + 新增需求）。需要批准后才动代码。**

---

## 1. 为什么要改

现在数据只在每台设备的 localStorage 里。手机上打开是空的，要再拖一次 CSV；
资产曲线的实测点 `valuePoints` 也是设备本地的，清网站数据就没了。
这两件事都只能靠一个共享存储解决。

## 2. 推翻的决策

[decisions.md](../../decisions.md) 里这一条：

> **Google Sheet 读写分离：读走公开 CSV 端点，写走 Apps Script**
> …代价：写路径依赖一个用户部署的服务。**缓解：读路径不依赖它，所以它挂了看板照常显示。**

那条方案要求 Sheet 设成「知道链接的人可查看」，因为 `gviz` 端点只对公开表返回数据。
Sheet ID 必须写进公开的 bundle，所以**任何人打开页面就能顺着读到整张表**。

当时这是可以接受的，因为用户说过不在乎数据被看到。**用户后来改了主意**
（「Google sheet 那边可以限制是吧」），所以前提没了，结论也得跟着变。

**新结论：Sheet 设为「仅自己」，读和写都走 Apps Script，都要令牌。**

代价说清楚：**上面加粗的那句缓解措施没有了**。Apps Script 挂了，看板就没有新数据。
第 8 节是对这一点的补偿。

## 3. 方案

```
楽天証券 CSV ──拖进页面──> 浏览器里解析 ──POST(令牌)──> Apps Script ──> Sheet（仅自己）
                                                              ^
基準価額メール ──每日触发器（gmail.readonly）───────────────────┘
```

- **Sheet**：仅自己可见。不发布、不共享链接。
- **Apps Script Web App**：部署成「以我的身份执行 / 任何人可访问」。
  这是唯一能让静态页面读到私有表的办法，且不需要建 GCP 项目、不过 OAuth 同意画面。
  **它的 exec URL 是公开的**，所以每个请求先验令牌，验不过什么都不做。
- **令牌**：用户自己生成，存进 Script Properties（服务端）和每台设备的 localStorage
  （客户端）。**不进仓库、不进 bundle、不经过我手。** 页面第一次打开时要求输入一次。
- **页面**：还是那个静态站，配置只有两项 —— exec URL（可以进 bundle，它本身不是秘密）
  和令牌（只在 localStorage）。

## 4. 未验证的前提 —— 先做一个 spike

**这个方案压在一个我无法在本地验证的假设上**：浏览器能不能跨域调用 Apps Script Web App
并读到响应。已知的坑：

- 跨域 POST 带 `Content-Type: application/json` 会触发 preflight `OPTIONS`，
  而 **Apps Script 不响应 OPTIONS**。通行做法是用 `text/plain` 发 JSON（简单请求，不预检）。
- Apps Script 的响应会从 `script.google.com` 跳到 `googleusercontent.com`，
  跨域下这一跳之后能不能读到 body，需要实测。

**所以第一步是一个 20 行的 spike**，只验四件事，从 `jackbaihaochen.github.io` 这个真实
来源发起（不是 localhost —— 来源本身是被测对象）：

1. GET 能否返回、JS 能否读到响应
2. POST `text/plain` 带 JSON 能否避开预检、JS 能否读到响应
3. 那一跳重定向之后 body 还读不读得到
4. 令牌错误时返回什么，形状和成功时是否一致

**如果第 2 项失败**，退路是只用 GET、令牌放 URL 里。那样令牌会进各种日志（浏览器历史、
Google 的访问日志），安全性明显更差 —— 写在这里是为了让它成为一个**被记下的退路**，
而不是做到一半才发现的意外。

### 结果（2026-09-03 实测、`jackbaihaochen.github.io` 上）

| 項目 | 結果 |
|---|---|
| GET | 200・リダイレクトを跨いで body を読めた |
| **POST `text/plain`** | **200・読めた ← これを使う** |
| POST `application/json` | `Failed to fetch`（preflight が通らない）**＝予測どおり** |
| POST `application/x-www-form-urlencoded` | 200・読めた（もう一つの退路として使える） |
| 誤ったトークン | `{"ok":false,"error":"denied"}` —— 成功時と同じ形 |

**退路は使わない。** `text/plain` が通ったので、トークンが URL に載る形は避けられた。
`src/sync/remote.ts` は書いたままでよい。

`application/json` の失敗はコンソールに CORS エラーとして出るが、**それは意図的に
失敗させた項目**であって不具合ではない。この一行が「なぜ text/plain なのか」の根拠になる。

> 这和我之前说的「别让你部署两次」不冲突。粘 20 行脚本点一次 Deploy 是一分钟的事；
> 把四张表、客户端重写、Gmail 触发器全压在一个没验证过的传输层上，才是贵的错误。

## 5. Sheet 里放什么

**放解析后的行，不放原始 CSV。** 单个单元格上限 5 万字符，而 JP 的交易履历有 56KB，
塞不进去。

| 表 | 内容 |
|---|---|
| `txns` | 交易明细（受渡日・区分・口座・銘柄・金额・flow）|
| `positions` | 最新快照的持仓 + `asOf` |
| `values` | `(日期, 総資産)` —— 资产曲线的实测点 |
| `entries` | 手动记录的投入 |
| `prices` | 基準価額（日期・ファンド名・価額），由每日触发器写入 |
| `meta` | `coverageEnd`、设置 |

**这里有一个要你明确点头的代价**：原方案在 localStorage 存原始 CSV，好处是
「解析器改好了，过去的导入也跟着变对」。存解析后的行就没有这个性质了 ——
**解析器修好之后，旧数据不会自动变对，得重新导入一次 CSV**。

缓解：原始 CSV 仍然留在**导入它的那台设备**的 localStorage 里，重新导入会覆盖 Sheet。
所以「重新导入」这个动作随时可做，只是不再自动。

## 6. 安全约束（硬性，写进代码评审）

- **Gmail 用 `gmail.readonly`**，不用 `GmailApp`（后者强制要 `https://mail.google.com/` 全权限）。
- **读邮件只能出现在时间触发器里，绝不能出现在 `doGet`/`doPost` 上。**
  exec URL 是公开的且以你的身份运行 —— 一旦请求路径能碰邮箱，它就成了你收件箱的公开代理。
- 令牌比较用固定时间比较，不用 `==` 提前返回。
- 令牌错误时返回和成功时**一样的形状**，不透露表存不存在、有没有数据。

## 7. 已有数据怎么办

你现在至少有一台设备的 localStorage 里存着手动记录和实测点。
**第一次带令牌打开、而 Sheet 是空的时候，页面会问你一次：把本机数据传上去，还是从空开始。**

不默认选任何一边。默认上传会在多设备时把旧数据覆盖新数据；默认清空会悄悄弄丢你记过的投入。
这个项目的整个立意就是数字要可信，这种地方不能替你决定。

## 8. Apps Script 挂了会怎样

第 2 节里丢掉的那条缓解，用这个补回来：**最后一次成功读到的数据缓存在 localStorage**。

- 读得到 → 正常显示
- 读不到 → 显示缓存，并在顶部明写「这是 X 月 X 日缓存的数据，现在连不上」
- 没有缓存 → 空页面 + 说明，不是白屏

页面已经有 `asOf` / `coverageEnd` 这套「这个数字是什么时候的」的机制，直接接上去。
